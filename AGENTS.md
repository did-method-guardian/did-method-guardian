# AGENTS.md

Instructions for an AI coding agent working in this repository. See [README.md](README.md) for what the project is; this file is about how to build, test, and change it correctly.

## Repository layout

- `packages/lib` -- the reference implementation of the `did:guardian` method itself (operation log replay, signature verification, threshold rules, key crypto, DID document rendering). `verifyLog` checks a log entirely on its own terms (§8); `resolve` builds on it to also verify a non-root identity's registrar attestation against its root's own log (§11) -- `resolve`, not `verifyLog` alone, is the complete check. Platform-agnostic (Web Crypto, no Node-specific APIs).
- `packages/server` -- a self-hostable registrar: `packages/lib` plus an HTTP surface, OIDC/OAuth2.1 identity provider, account dashboard, admin console, and agent-identity API. Runs as a Cloudflare Worker.
- `packages/cli` -- `@did-guardian/cli` on npm: a command-line tool built on `packages/lib`, for key management, registration, resolution/verification, and guardianship end to end, against any conformant registrar.
- `interop_tests` -- the conformance suite: `cleanroom/vectors-final/*.json`, fixtures any independent implementation should replay and verify the same way this one does. Generated by `cleanroom/gen.py`, never hand-typed; `cleanroom/verifier.py` is a from-scratch clean-room reference verifier, and `cleanroom/run.py` replays every vector against it.
- `website` -- this project's own site (the guide, the formal specification, the registrar API doc), built with `hyperctl` (HyperTemplates) and deployed to guardianspec.org as a Cloudflare Worker with static assets.

## The rule that matters most: the spec and `packages/lib` change together

`website/content/docs/did-guardian-spec-v1.0.0/index.md` is the normative definition of the method. `packages/lib/src/*.ts` is its reference implementation. Never change one without checking the other:

- A new or changed requirement (`REQ-<section>-<n>`) needs the corresponding logic in `packages/lib/src/rules.ts`/`operations.ts`/`document.ts`, and usually a new fixture in `interop_tests/cleanroom/`, generated via `gen.py`, not hand-written.
- A behavior change in `packages/lib` that isn't already covered by a `REQ-` id in the spec needs one added there first -- an implementation detail the spec doesn't require isn't safe to rely on.
- Requirement ids are permanent once published: a new rule in an existing section gets the next free number, regardless of where in the section it's placed. Never renumber or reuse an id.
- `packages/lib/schemas/*.schema.json` and `website/static/requirements.json` are both derived from the spec/types -- see "Generated files" below. Regenerate them after any change to either.

## Build and test

```bash
# packages/lib
cd packages/lib
npm run build   # tsc -p tsconfig.build.json
npm test        # builds, then runs dist/tests/*.test.js (node:test)

# packages/server
cd packages/server
npm run build   # tsc --noEmit (typecheck only -- wrangler bundles directly from TS at deploy time)
npm test        # tsx --test tests/*.test.ts

# packages/cli
cd packages/cli
npm run build   # tsc -p tsconfig.build.json
npm test        # builds, then runs dist/tests (node:test)

# from the repo root
npm run build   # wraps packages/lib's build
npm test        # wraps packages/lib's test
```

All three suites must pass before considering a change done. Only `packages/lib` is wired into the root `package.json` scripts -- run `packages/server`'s and `packages/cli`'s build/test from inside each package directly.

## Generated files -- regenerate, don't hand-edit

Each of these is produced by a script from some other source of truth. Hand-editing the output will just be overwritten the next time the script runs, and will drift from the thing it's supposed to mirror in the meantime. CI (`.github/workflows/ci.yml`'s `website-sync` job) reruns every one of these on every push and fails the build if that produces a diff, so a forgotten regeneration is caught there even if it's missed locally.

| Generated file | Script | Source of truth |
|---|---|---|
| `interop_tests/cleanroom/vectors-final/*.json` | `interop_tests/cleanroom/gen.py` (`python3 gen.py` in `interop_tests/cleanroom`) | the spec text, read clean-room |
| `website/static/requirements.json` | `website/scripts/gen-requirements.py` | The spec's own `<a id="req-...">` anchors, plus test file names |
| `packages/lib/schemas/**` | `website/scripts/sync-schemas.py` | `website/static/schemas/**` -- hand-written there first (matching `types.ts`), then synced into `packages/lib/schemas` directly (byte-identical; see that script's own header comment for why the direction runs this way, not the other) |
| `website/static/docs/**/*.md`, and `website/src/index.ts`'s `MARKDOWN_TWIN_PATHS` (between its own marker comments) | `website/scripts/sync-md-twins.py` | `website/content/docs/**/index.md` |
| `website/static/llms-full.txt` | `website/scripts/gen-llms-full.py` | `website/content/docs/**/index.md` |
| `website/static/sitemap.xml` | `website/scripts/gen-sitemap.py` | `website/content/docs/**/index.md` |

## Deploying the website

```bash
cd website
python3 scripts/sync-md-twins.py
python3 scripts/gen-requirements.py
python3 scripts/sync-schemas.py
python3 scripts/gen-llms-full.py
python3 scripts/gen-sitemap.py
hyperctl build complete -c site.yaml
ln -sfn <new-build-uuid> builds/current
npx wrangler deploy --config wrangler.jsonc
```

Live-verify after every deploy -- Cloudflare's edge cache can briefly serve the previous version even after a successful deploy; re-check without a cache-busting query param before concluding something is broken.

## Deploying the registrar

`packages/server` deploys identically to two live registrars sharing the same code:

```bash
cd packages/server
npx wrangler deploy --config wrangler.guardianspec.jsonc
npx wrangler deploy --config wrangler.zz.jsonc
```

Check both after any change that touches shared code -- a fix verified on one and not the other isn't done.
