# AGENTS.md

Instructions for an AI coding agent working in this repository. See [README.md](README.md) for what the project is; this file is about how to build, test, and change it correctly.

## Repository layout

- `packages/lib` -- the reference implementation of the `did:guardian` method itself (operation log replay, signature verification, threshold rules, key crypto, DID document rendering). Platform-agnostic (Web Crypto, no Node-specific APIs).
- `packages/server` -- a self-hostable registrar: `packages/lib` plus an HTTP surface, OIDC/OAuth2.1 identity provider, account dashboard, admin console, and agent-identity API. Runs as a Cloudflare Worker.
- `interop_tests` -- operation-log fixtures (`operation_log/valid/`, `operation_log/invalid/`) any independent implementation should replay and verify the same way this one does. Generated by `packages/lib/scripts/gen-fixtures.ts`, never hand-typed.
- `website` -- this project's own site (the guide, the formal specification, the registrar API doc), built with `hyperctl` (HyperTemplates) and deployed to guardianspec.org as a Cloudflare Worker with static assets.

## The rule that matters most: the spec and `packages/lib` change together

`website/content/docs/did-guardian-spec-v0.2.0/index.md` is the normative definition of the method. `packages/lib/src/*.ts` is its reference implementation. Never change one without checking the other:

- A new or changed requirement (`REQ-<section>-<n>`) needs the corresponding logic in `packages/lib/src/rules.ts`/`operations.ts`/`document.ts`, and usually a new fixture in `interop_tests/` generated via `gen-fixtures.ts`, not hand-written.
- A behavior change in `packages/lib` that isn't already covered by a `REQ-` id in the spec needs one added there first -- an implementation detail the spec doesn't require isn't safe to rely on.
- Requirement ids are permanent once published: a new rule in an existing section gets the next free number, regardless of where in the section it's placed (`REQ-7.2-11` is the one existing example of this). Never renumber or reuse an id.
- `packages/lib/schemas/*.schema.json` and `website/static/requirements.json` are both derived from the spec/types -- see "Generated files" below. Regenerate them after any change to either.

## Build and test

```bash
# packages/lib
cd packages/lib
npm run build   # tsc -p tsconfig.build.json
npm test        # builds, then runs dist/tests/*.test.js (node:test)

# packages/server
cd packages/server
npm run build   # tsc --noEmit (typecheck only -- wrangler bundles directly from TS at deploy time)
npm test        # tsx --test tests/*.test.ts

# from the repo root
npm run build   # wraps packages/lib's build
npm test        # wraps packages/lib's test
```

Both suites must pass before considering a change done. `packages/server` is **not** wired into the root `package.json` scripts -- run its build/test from `packages/server` directly.

## Generated files -- regenerate, don't hand-edit

Each of these is produced by a script from some other source of truth. Hand-editing the output will just be overwritten the next time the script runs, and will drift from the thing it's supposed to mirror in the meantime.

| Generated file | Script | Source of truth |
|---|---|---|
| `interop_tests/operation_log/**/*.json` | `packages/lib/scripts/gen-fixtures.ts` (`npm run gen-fixtures` in `packages/lib`) | `packages/lib`'s own signing/verification code |
| `website/static/requirements.json` | `packages/lib/scripts/gen-requirements.py` | The spec's own `<a id="req-...">` anchors, plus test file names |
| `website/static/schemas/**` | `website/scripts/sync-schemas.py` | `packages/lib/schemas/**` (hand-written, matching `types.ts`) |
| `website/static/docs/**/*.md` | `website/scripts/sync-md-twins.py` | `website/content/docs/**/index.md` |
| `website/static/llms-full.txt` | `website/scripts/gen-llms-full.py` | `website/content/docs/**/index.md` |

## Deploying the website

```bash
cd website
python3 scripts/sync-md-twins.py
python3 ../packages/lib/scripts/gen-requirements.py
python3 scripts/sync-schemas.py
python3 scripts/gen-llms-full.py
hyperctl build complete -c site.yaml
# Chroma (hyperctl's syntax highlighter) bakes <span class="ln">N</span>
# line-number markup into every highlighted code block with no config to
# disable it -- strip it from the fresh build before deploying, or an
# agent/crawler reading the raw HTML gets line numbers glued onto the code:
python3 -c "
import re, glob
pattern = re.compile(r'<span class=\"ln\">\s*\d+</span>')
for f in glob.glob('builds/<new-build-uuid>/docs/**/index.html', recursive=True):
    c = open(f, encoding='utf-8').read()
    if 'class=\"ln\"' in c:
        open(f, 'w', encoding='utf-8').write(pattern.sub('', c))
"
ln -sfn <new-build-uuid> builds/current
npx wrangler deploy --config wrangler.jsonc
```

Live-verify after every deploy -- Cloudflare's edge cache can briefly serve the previous version even after a successful deploy; re-check without a cache-busting query param before concluding something is broken.

## Deploying the registrar

`packages/server` deploys identically to two live registrars sharing the same code:

```bash
cd packages/server
npx wrangler deploy --config wrangler.guardianspec.jsonc
npx wrangler deploy --config wrangler.zz.jsonc
```

Check both after any change that touches shared code -- a fix verified on one and not the other isn't done.
